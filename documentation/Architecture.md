# Architecture

This document records the technical architecture of Lumina Chronica and — critically — the reasoning behind every decision that isn't already pinned down in the [Master Project Bible](master-project-bible/) or [Technical Standards](Technical-Standards.md). Per the AI Development Guidelines, architecture decisions must be explained, and the six protected decisions below must not be changed without justification (why / advantages / disadvantages / impact).

## Protected architectural decisions

Not to be changed without explicit justification:

- **Blazor WebAssembly** (frontend)
- **Cloudflare architecture** (Workers / D1)
- **Monorepo** (single repository for frontend + backend + docs)
- **D1 database**
- **Modular structure** (feature-based modules: Reader, Library, Project, Community, AI)
- **Cloudflare R2** (file storage) — decided 2026-07-29 when Phase 3 (Library) was planned; see the table below.

## Stack

| Layer | Technology | Hosting |
|---|---|---|
| Frontend | Blazor WebAssembly, .NET 10 | GitHub Pages |
| Backend | Cloudflare Workers, TypeScript, [Hono](https://hono.dev) | Cloudflare |
| Database | Cloudflare D1 (SQLite-compatible) | Cloudflare |
| File storage | Cloudflare R2 | Cloudflare |
| API style | REST, JSON, base path `/api/` | — |

Data flow: `User → Blazor WASM (GitHub Pages) → Cloudflare Worker API (/api/*) → D1 / R2`.

## Repository structure

```
lumina-chronica/
  frontend/LuminaChronica.Client/   Blazor WASM app
    Pages/ Components/ Services/ Models/ Layouts/ Styles/ Assets/
  backend/                          Cloudflare Worker API
    src/{routes,services,middleware,models,utils}, index.ts
  database/
    migrations/                     0001_initial.sql, 0002_books.sql, ..., never edited after merge
  shared/                           Cross-stack shared contracts/types (created when something concrete needs it)
  documentation/                    This file, Roadmap, Database docs, Master Project Bible, Technical Standards
  tests/
    frontend/                       bUnit component tests
    backend/                        Vitest tests
  scripts/                          Dev/deploy helper scripts (created when something concrete needs it)
```

Per Technical Standards §5 (binding), this list is authoritative over the Master Project Bible's own repo-structure sketches (Teil 3 §… and the Implementation Blueprint's Phase 0), which are slightly narrower.

## Decisions made where the source docs left a gap

Every decision below follows the project's own priority order (Technical Standards §11 / AI Development Guidelines §85): **Verständlichkeit/Simplicity → Wartbarkeit/Maintainability → Benutzerfreundlichkeit/UX → Performance → Erweiterbarkeit/Extensibility.**

| Area | Decision | Reasoning |
|---|---|---|
| Backend router | [Hono](https://hono.dev) | No router is named in the Master Project Bible. Hono is the standard lightweight, Workers-native router; its built-in `hono/cors` middleware directly handles cross-origin requests between the GitHub Pages frontend and the `workers.dev` backend, including OPTIONS preflight. CORS is configured to allow only the known frontend origin(s), per Technical Standards §7 ("CORS wird restriktiv konfiguriert"). |
| D1 binding | Database `lumina-chronica-db`, Worker binding name `DB` | Not specified anywhere in the source docs; simple conventional name. |
| File storage (books/covers) | **Cloudflare R2**, one bucket `lumina-chronica-storage`, Worker binding `STORAGE`. Decided 2026-07-29 when Phase 3 (Library) was planned. Google Drive and Supabase Storage were evaluated as card-free alternatives (Drive: OAuth complexity, no clean public URLs, not designed as a file server; Supabase: 1GB free cap, auto-pauses after 7 days idle) — the user chose R2 anyway after seeing those concrete tradeoffs, reversing the earlier "avoid adding a card" stance specifically for R2. | R2 is a native Worker binding (`env.STORAGE.put/get/delete`) — no cross-origin credential dance, no extra account, no signed-URL/CORS setup the alternatives would need. |
| R2 key layout | `books/{book-id}/original.{ext}` (book file), `books/{book-id}/cover.{ext}` (cover) — extension matches the actual uploaded format. | Technical-Standards.md §4 specifies `original.epub`/`cover.jpg` literally, but hardcoding `.jpg` would force re-encoding every non-JPEG cover (extra CPU, extra image library) just to match a naming convention. Keeping the real extension is a small, deliberate deviation. |
| Upload limits | Book file: 50MB max. Cover image: 5MB max. Allowed book formats: `.epub .pdf .txt .md` (extension-authoritative; MIME is only checked where reliable — EPUB/PDF — since `.txt`/`.md` MIME types are inconsistent across browsers/OSes). Allowed cover formats: `.jpg .jpeg .png .webp`. | Cloudflare Workers' free-plan request-body cap is 100MB, but the real constraint is the 128MB per-isolate memory limit, since `c.req.parseBody()` materializes the whole multipart body in memory before `R2Bucket.put()` is called. **Benchmarked against real `workerd`** (`wrangler dev --local`, not Node) before implementation: 5 repeated 50MB multipart uploads parsed consistently in ~1.8-1.9s with no crashes or memory issues, confirming the single-endpoint multipart design (`POST /api/books/upload`) is safe at this size — same benchmark-before-committing approach used for the PBKDF2 iteration count in Phase 2. |
| Metadata extraction on upload | **Manual entry only** — the upload form has explicit fields (title, author, description, genre, language, isbn, publisher, releaseDate, pages, tags); nothing is parsed out of the uploaded EPUB/PDF file itself. | Per-format parsing (EPUB OPF metadata, PDF page count) is unspecified complexity that would need its own CPU-budget benchmark against the same 10ms/request ceiling PBKDF2 hit. Reading "EPUB, PDF, TXT, Markdown" in the source spec's Upload item as *accepted upload formats* (validated, stored as-is) rather than *formats to parse* satisfies the phase's DoD without that risk — Phase 4 (Reader) has to parse these formats to render them anyway. |
| `GET /api/books` scope | Auth required; always scoped to the caller's own books (`owner_id = current user`). The `visibility` column (`PRIVATE`/`SHARED`/`PUBLIC`) is stored but not enforced for cross-user access yet — every upload defaults to `PRIVATE`. | No public/shared browsing surface exists anywhere in the app yet. Building visibility-aware access control now would be dead code with no consumer. |
| Book file/cover serving | `GET /api/books/:id/file` and `GET /api/books/:id/cover` — auth+ownership-checked, stream the R2 object's bytes directly through the Worker rather than exposing a public bucket URL. Not in the source spec's 4 documented book endpoints. | Database Rules §58 explicitly forbids returning private content without a permission check, so R2 objects can't be served from a bare public bucket URL once `visibility` is meaningful. Frontend `<img src>` can't attach an `Authorization` header, so covers are fetched via `ApiClient` (bearer token attached like any other call) and turned into a `URL.createObjectURL(...)` blob URL for display — see `BlobUrlService`/`wwwroot/js/blobUrl.js`. |
| Migrations | `database/migrations/0001_initial.sql`, `0002_...` — 4-digit, per Technical Standards §3. Existing migrations are never edited; every schema change is a new file. | Explicit, binding convention; also matches `wrangler d1 migrations`' own default numbering, so no tooling mismatch. |
| API response envelope | Every JSON response: success → `{"success": true, "data": {...}}`; error → `{"success": false, "error": {"code": "...", "message": "..."}}`. Standard HTTP status codes per Technical Standards §2. | Explicit, binding convention (Technical Standards §2) — supersedes the one bare `{"status":"online"}` example in the Implementation Blueprint, which predates this convention. |
| Password hashing | WebCrypto `PBKDF2-HMAC-SHA256` via `crypto.subtle`, **8,000 iterations**. Stored in the existing `users.password_hash` column as `pbkdf2$<iterations>$<base64url-salt>$<base64url-hash>` (`backend/src/utils/crypto.ts`). | bcrypt/argon2 rely on native modules unavailable in Workers; PBKDF2 is native to `crypto.subtle`. The iteration count was **benchmarked against the real Workers runtime** (`wrangler dev --local`, same workerd engine as production): 50,000 iterations already takes ~33ms, over 3x the Workers Free plan's 10ms CPU-time-per-request budget (exceeding it fails the request outright, error 1102). 8,000 iterations leaves solid headroom. This is below current OWASP guidance (600,000) for PBKDF2-HMAC-SHA256 — a deliberate, documented tradeoff for staying on the free Workers plan, confirmed with the user (2026-07-29): stay free with weaker hashing rather than move to Workers Paid ($5/mo) for stronger hashing. Revisit only if the project ever moves to a paid plan. Encoding the algorithm/iterations/salt into the existing TEXT column avoided a migration and makes future per-row iteration bumps possible without a global rehash. |
| Auth token | Custom JWT (HS256), implemented directly with `crypto.subtle.sign`/`.verify` (no `jsonwebtoken`/`jose` dependency — the payload is 3 fields). Claims: `{ sub, role, iat, exp }`. Expiry: **7 days**, no refresh-token flow. Secret: `JWT_SECRET`, set via `wrangler secret put` (never committed, not in `wrangler.toml`) — must be re-set if the Worker is ever recreated. | Teil 3 lists Cloudflare Access as a *preferred option in principle*, but the actually-documented API (Teil 4 §53) is a custom-auth shape returning a bearer token — the concrete, already-specified API takes precedence. Implemented in Phase 2 (PR #33). |
| Login identifier | `POST /api/auth/login`'s request body field is `identifier` (matches against either `email` or `username`), not `email` as the source spec's one example shows. Response shape is unchanged (`{"token":"jwt-token","userId":1}`). | Added same-day as a Phase 2 follow-up (PR #42) after the user asked why login couldn't accept a username — this row exists because the field-name change was implemented but never previously written down here. |
| Token storage (frontend) | `localStorage`, key `lumina_auth_token`, via a `TokenStore`/JS-module wrapper (`wwwroot/js/auth.js`) mirroring `ThemeService`'s pattern. Attached to requests via a `DelegatingHandler` (`AuthHeaderHandler`); a custom `AuthenticationStateProvider` (`LuminaAuthStateProvider`) decodes the JWT payload client-side (signature already verified server-side) to drive `<AuthorizeView>`/`[Authorize]`. | Simplest option, matches the existing plain-`HttpClient` `ApiClient`. Cross-origin HttpOnly cookies would need `SameSite=None; Secure` + `credentials:"include"` on every request for no clear benefit here. **Tradeoff**: localStorage is readable by any script on the page, so an XSS bug would leak the token — mitigated for now by the app rendering no untrusted user-generated HTML anywhere. Revisit if/when rich-text content (comments, community features) is added in v3.0. Implemented in Phase 2 (PR #35). |
| Auth middleware / endpoint auth rules | `backend/src/middleware/auth.ts`'s `requireAuth`, applied per-route (not globally). Public: `POST /api/auth/register`, `POST /api/auth/login`. Auth required: `POST /api/auth/logout`, `GET/PUT /api/users/me`. No role-gated endpoints yet — `USER`/`ADMIN` is carried in the token for future use, but nothing in the app currently has an admin-only surface. | Resolves Open Question #19 (no endpoint-level auth table in the source docs) for Phase 2's routes specifically. Each future phase should document its own routes' auth requirement here rather than relying on one blanket rule, since e.g. Library's `GET /api/books` will likely need public/private distinctions per resource, not a blanket rule. |
| CSS approach | Plain CSS with CSS custom properties (`--color-*`, `--space-*`) per theme; no CSS framework. | No framework is named anywhere in the source docs. Custom properties work natively with Blazor's CSS isolation and make runtime theme-switching (4 themes) a matter of toggling a root attribute. |
| Spacing scale | 8px grid: `--space-1: 8px` … `--space-8: 64px` (8/16/24/32/48/64). | Technical Standards §1, explicit and binding. |
| Color tokens (exact hex values) | **Decided 2026-07-29** via the `frontend-design` skill (deferred here since Phase 1, now that real page layouts exist to design against): "reading room by day/candlelight" — brass/gilt-lettering primary accent, oxblood-leather secondary accent, aged-paper backgrounds, iron-gall-ink text. `classic-library.css` (day) and `dark-library.css` (night) carry the actual palette; `modern-light`/`system` are untouched in character (deliberately the non-library option, per Teil 5's own "hell, minimalistisch, clean" description). `--color-secondary`/`--color-gold-accent` existed as unused placeholder tokens since Phase 1 scaffolding and are now wired into real UI (progress bars, active-nav underline, the heading-rule signature below). | Token *names* were already fixed (Technical Standards §1); only hex values were open. Two named "materials" (brass, oxblood) reused consistently across components read as more deliberate than a single generic "brown" accent. |
| Typography (real typefaces) | **Decided 2026-07-29**, self-hosted (SIL OFL, vendored under `wwwroot/fonts/` like epub.js/pdf.js — no Google Fonts CDN dependency): [Fraunces](https://github.com/undercasetype/Fraunces) (display serif, old-style ink-trap character) for headings/wordmark, used at 400/600/700 weight; [Literata](https://github.com/googlefonts/literata) (reading serif, designed for on-screen reading) for the Reader page and long-form text — this was already named in `tokens.css`'s font stack since Phase 1 but never actually loaded, silently falling back to Georgia. UI chrome (nav, buttons, forms) stays on the plain system-font stack on purpose, so the display serif's personality isn't diluted by overuse. Only the Latin subset is vendored (`U+0000-00FF` covers German ä/ö/ü/ß). | A distinctive display serif used sparingly carries more character than styling the existing system-font stack further; self-hosting matches the project's established no-runtime-CDN-dependency stance. |
| Heading signature device | Every page `<h1>` gets a 3px double-line rule under it in the gold-accent color, sized to the title's own width (`width: fit-content`) rather than the full page width. | Echoes the rule under a chapter heading in an old book — literal to the subject rather than decorative, and gives every page a consistent, recognizable marker without needing per-page custom design. |
| Icons | Literal Unicode/emoji glyphs matching the Master Project Bible's own nav icon set (🏠 📚 🌎 🌍 📊 👤 ⚙), **except** the book-cover placeholder (`BookCard`), which is now a small inline line-drawn SVG book glyph in the muted-text color — the emoji's saturated colors clashed with the refined palette on every book without a cover, a much more visible/repeated element than the nav icons. Nav emoji unchanged. | No icon library is named anywhere; the source docs use emoji directly. Revisit in V1.5 if this doesn't hold up visually at scale. |
| Testing | bUnit for Blazor components (`tests/frontend/`); Vitest for the Worker (`tests/backend/`). | No framework is named in the docs; these are the standard choice for each respective stack. |
| License | MIT | Not specified; simplest permissive default for a public portfolio repository. |
| CI/CD | GitHub Actions. Frontend build+deploy to GitHub Pages is fully automated (uses the built-in `GITHUB_TOKEN`). Backend `wrangler deploy` workflow exists but requires the repository owner to add a `CLOUDFLARE_API_TOKEN` secret before it can run — that's an account-security action only the owner should perform. Until then, backend deploys are run manually via an already-authenticated local `wrangler` session. | GitHub Actions can't reuse a local OAuth `wrangler` session; CI needs a scoped API token. |
| GitHub Pages + Blazor WASM deploy correctness | `.nojekyll` in the published output (GitHub Pages runs Jekyll by default, which ignores `_`-prefixed folders like Blazor's `_framework/`); `<base href>` is `/` in source (so `dotnet run` works locally) and rewritten to `/lumina-chronica/` by a `sed` step in `frontend-deploy.yml` only in the published output (must match the repo name); `404.html` = a copy of the published `index.html` so client-side routes survive a hard refresh. | None of the source documents mention Blazor+Pages deployment mechanics at all; without these, the deployed app 404s on load or on refresh, or local dev breaks if the subpath were hardcoded into source. |
| `reading_progress.position` type | `TEXT`, not the `FLOAT` shown in the source spec's extracted field table — a deliberate, documented deviation (same category as `cover.{ext}` vs. the spec's literal `cover.jpg` in Phase 3). Per-format meaning: EPUB → CFI string (`epubcfi(...)`), resumed via `rendition.display(cfi)`; PDF → current page number as a string; TXT/MD → scroll fraction (`"0.6300"`) as a string. `percentage FLOAT` stays numeric (0–100) for all formats. `chapter INTEGER` is also format-specific: EPUB → spine/TOC index (not yet used — story 1 only implements TXT/MD), PDF → page number, TXT/MD → unused (`NULL`). | An EPUB CFI is what makes resume actually precise and fast — `rendition.display(cfi)` resumes immediately with no book-wide parsing, unlike percentage-based resume which needs epub.js's `book.locations.generate()` (parses the entire spine on every open). `FLOAT` can't hold a CFI string. |
| `reading_progress` upsert | `INSERT ... ON CONFLICT(user_id, book_id) DO UPDATE`, backed by a `UNIQUE(user_id, book_id)` constraint on the table. | Keeps "save progress" idempotent per user+book without a separate read-then-write round trip. |
| Reader font size | Client-local only (`localStorage`, `wwwroot/js/readerSettings.js`, mirroring `theme.js`/`ThemeService`) — **not** synced to `user_settings.font_size`/`theme`/`reader_mode`, which stay unused (same as `role`/`avatar_url` from earlier phases). | The app-wide theme picker (`Settings.razor`/`ThemeService`) is already client-local-only with no settings-sync endpoint anywhere in the app; building account-sync just for the reader would be inconsistent scope creep. Revisit only if a real settings-sync feature is planned. |
| Markdown rendering | [Markdig](https://github.com/xoofx/markdig) (NuGet, pure C#, runs in Blazor WASM), with **raw HTML passthrough disabled** in the pipeline (`MarkdownPipelineBuilder().DisableHtml()`). TXT is rendered as plain preformatted text. | Keeps Markdown parsing in the C# ecosystem instead of adding a JS library for something Markdig already does. Disabling raw HTML matters specifically because the "Token storage (frontend)" row above justifies `localStorage` JWT storage on the premise that "the app renders no untrusted user-generated HTML anywhere" — an unfiltered Markdig pipeline would let an uploaded `.md` file's embedded `<script>` break that premise. Verified: `<script>` tags in uploaded Markdown do not appear in the rendered output. |
| Reader progress-save trigger | Debounced periodic save (every 15s while the reader page is open) plus an explicit save on component dispose (navigating away). No save-on-every-scroll-tick. | Avoids spamming `POST /api/reading/update` on every pixel of scroll. |
| EPUB library | [epub.js 0.3.93](https://github.com/futurepress/epub.js) + its [JSZip 3.10.1](https://stuk.github.io/jszip/) dependency, vendored as static UMD builds under `wwwroot/lib/epubjs/` (`jszip.min.js`, `epub.min.js`; no CDN, no npm build step). Lazy-loaded via `<script>` injection from `wwwroot/js/epubReader.js` on first EPUB open, not referenced from `index.html`, since most page loads never open an EPUB. Load order is sequential (JSZip, then epub.js) — epub.js's browser-globals UMD path reads `window.JSZip` at eval time, not lazily. Rendition uses `flow: "paginated"` (chapter-relative pagination with next/prev controls), and `rendition.themes.fontSize(...)` for the font-size control (epub.js renders into an iframe, so page-level CSS variables don't reach it). | Only realistic client-side EPUB renderer; no Blazor-native equivalent exists. Vendoring matches how this project avoids external runtime dependencies everywhere else (same stance as R2 vs. a public bucket URL, PBKDF2 vs. a CDN-hosted crypto library, etc.). |
| EPUB progress/resume | Resume uses the CFI string directly (`rendition.display(cfi)`) — see the `reading_progress.position` row above. `percentage` is a best-effort estimate from the current spine index ÷ `book.spine.length`, computed on every `relocated` event; `chapter` stores that same spine index. Deliberately **not** using epub.js's `book.locations.generate()` for percentage, which parses the entire spine on every open. | Resume correctness never depends on the percentage estimate — only the CFI does that job, and it's exact. The spine-index estimate is cheap (no parsing) and good enough for a progress indicator; `locations.generate()`'s precision isn't worth its cost here. |
| PDF library | [pdf.js 6.2.108](https://mozilla.github.io/pdf.js/), vendored under `wwwroot/lib/pdfjs/` as `pdf.min.mjs` + `pdf.worker.min.mjs` — the **modern ES module build**, not the UMD build the original plan assumed, since pdf.js v4+ ships ESM only (no classic-script build exists anymore). `wwwroot/js/pdfReader.js` is itself a module that `import`s `pdf.min.mjs` via a relative specifier and sets `GlobalWorkerOptions.workerSrc = new URL("../lib/pdfjs/pdf.worker.min.mjs", import.meta.url).href` — resolved against the *module's own URL*, not a leading-slash absolute path, avoiding the same class of GitHub Pages subpath bug as issue #38. Rendering is single-page canvas (`page.render({canvasContext, viewport})`), scaled to the container's width, with next/prev controls; no continuous-scroll or multi-page view. | Only realistic client-side PDF renderer; matches the epub.js vendoring approach. The worker-path pattern is pdf.js's own documented recommendation for module builds and is inherently base-relative, unlike a hand-rolled string path. |
| PDF progress/resume | `chapter` and `position` both store the current page number (`position` as a string, matching the `reading_progress.position` row's `TEXT` type); `percentage` = `page / pageCount * 100`. Resume calls `init(..., initialPage)` directly with the saved page — no CFI-equivalent concept exists for PDF, page number is already exact. | Simplest possible mapping; PDF pages are a fixed, unambiguous unit of position, unlike EPUB's reflowable content. |
| Razor component parameter binding gotcha (EPUB/PDF readers) | `<EpubReader InitialCfi="_initialCfi">`/`<PdfReader InitialPage="_initialPage">`-style component attributes **must** use `@` (`InitialCfi="@_initialCfi"`) when the bound C# value is a field/variable reference, not literal text. | A real bug shipped and reached production because of this: `InitialCfi="_initialCfi"` (no `@`) compiled successfully — `InitialCfi` is `string?`, so the bare identifier type-checked as the **literal string** `"_initialCfi"` — and every EPUB open silently passed that garbage string as the resume CFI, failing with epub.js's `"No Section Found"` on every single book (issue #75/PR #76). Non-string-typed parameters (`byte[] Bytes`, `int FontSize`/`InitialPage`) don't have this failure mode, since a bare identifier can't type-check as a literal against those types — only `string`/`string?` parameters are at risk. Caught only via live end-to-end testing with a real file, not by any compiler warning or automated test; a targeted bUnit regression test now asserts the child component actually receives the field's value (`cut.FindComponent<EpubReader>().Instance.InitialCfi`), not just that the page renders. |
| Upload metadata extraction | `wwwroot/js/metadataExtractor.js` runs entirely client-side on the Upload page, reusing the already-vendored epub.js (`book.loaded.metadata`/`book.loaded.cover` → `book.archive.getBlob(path)`) and pdf.js (`doc.getMetadata()` + page-1 canvas render) from the Reader stories — no backend endpoint, no server-side parsing. Extraction only fills form fields the user hasn't already typed into; TXT/MD are skipped (no container-level metadata to extract). Verified against real files in `bookDownloads/`: epub.js's `metadata.identifier` is frequently a UUID rather than an ISBN (e.g. every epubBooks.com/Blyton title), so the ISBN field is only filled if the value has ISBN-10/13 shape after stripping separators; a PDF `info.Title` that looks like a filename (`.doc`/`.pdf` suffix) is also skipped. Extracted covers upload via a new `ByteArrayContent` path (`BuildExtractedCoverContent`) alongside the existing `IBrowserFile` one, reusing the `QuoteFieldName` RFC 7578 fix. (Issue #86/PR #87) | Reusing the Reader's vendored libraries avoided adding a third parsing dependency; running extraction client-side sidesteps the Workers 10ms CPU-budget limit entirely, since no bytes are parsed server-side. The UUID-vs-ISBN and filename-vs-title guards came directly from probing real downloaded books rather than assuming the metadata APIs return clean data — an empty field beats a wrong one. |
